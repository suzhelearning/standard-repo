# Feature Map 与确定性护栏设计

v2.0 的核心问题把目录架构与工程验证合二为一：**使用者从哪个入口完成什么动作？哪些边界一旦越过就必须由程序而非人工挡住？**

## 1. 从《All Code Is Slop (Except Mine)》确立的四条工程原则

| Lauren Tan (poteto) 的核心观察 | standard-repo v2.0 的架构转化 |
| --- | --- |
| **目录编码进程与边界（Dune）**：用目录名显式区分 Electron 主/渲染进程，用依赖检查拦截越界导入。[图文与演示](https://ai.engineer/talks/O_zcc6Xl12g-all-code-is-slop-except-mine) | 目录即边界。每种[仓库类型](repository-types.md)都显式声明“禁止越界”清单，高频雷区落入静态检查或构建规则，而非仅写在文档里。 |
| **仓库即 Agent 样板（Software Garden）**：Agent 会照抄已有代码；反复出现的评审意见必须转成可执行检查。[逐字稿，约 1:03:27 起](https://ai.engineer/code/2026/talks/lauren-tan) | 清理重复实现与失效示例，推行“**第二次即固化**”：同类结构或边界错误第 2 次出现时，升格为不可错接口（L2）或离线检查脚本（L3），报错直接给出修复指引。 |
| **功能地图驱动真实验收（Feature Map）**：用用户视角命名操作，再用可重复工具真实驱动应用。[功能地图幻灯片](https://ai.engineer/api/talk-essay-media/0a57dd9b23616685acb085340c05e2583095347dc8f0ddb0fea3b4f5943aa210) | 将 **Feature Map** 设为仓库一等契约，映射“用户动作 → 唯一正式入口 → 最小样本 → 确定性证据”，同时指导目录划分与[整理盘点](migration.md)。 |
| **证据先于信任与发布闭环**：先证明改动可正确交付，再复用同一验证流接入发版。[发布章节](https://ai.engineer/talks/O_zcc6Xl12g-all-code-is-slop-except-mine) | 本地、PR 与发布标签运行同一条离线检查命令。本仓用零依赖脚本校验全部文档契约；业务仓按真实故障选择回放、属性测试或现场验收。 |

## 2. 约束防滑坡阶梯（L0 → L3）与治理铁律

在 Agent 高频修改的仓库里，纯文字约束是最脆弱的防线。应尽可能把关键边界向上推进：

| 等级 | 约束形式 | 抗 Slop 能力 | 典型落地 |
| --- | --- | --- | --- |
| **L0** | 散文规则（README / AGENTS.md） | 弱：易被遗忘或辩解绕过 | 原则说明、背景知识 |
| **L1** | 结构信号（目录命名、单一权威位置） | 中：引导人与 Agent 找准落点 | `src/` vs `examples/`、`outputs/` 忽略 |
| **L2** | 不可错接口（类型/Schema/读入校验） | 强：非法状态无法构造或直接报错 | 轨迹读入强制校验坐标系与长度单位 |
| **L3** | 确定性检查（离线脚本、Lint、依赖图、回归） | 最强：提交与发布前自动拦截 | `scripts/check_release.py`、边界导入检查 |

**三条治理铁律**：
1. **第二次即固化（Review-to-Guardrail）**：同一类越界、断链、配置漂移或接口误用在第 2 次评审中重现时，不再追加散文提示，直接补一条 L2 校验或 L3 检查。
2. **报错自带修复指令（Agent-Actionable Diagnostics）**：L3 检查输出必须包含**文件/位置 + 违反的契约 + 具体修复动作**（例如 `docs/repository-types.md: add forbidden-boundary section for app`），让人类与 Agent 都能一次修对。
3. **封堵逃生舱（No Silent Escape Hatches）**：禁止用静默 fallback、吞掉异常的兜底分支或无理由的全局 lint 忽略注释绕过边界检查。

## 3. Feature Map 标准格式与七类目标护栏配方

每个标准仓库在 `README.md`（小仓）或 `docs/feature-map.md`（大仓）维护一张精简表：

```text
| 用户动作 | 唯一正式入口 | 最小代表样本 | 确定性断言与证据 |
```

下表列出六类核心原型与多仓拓扑的典型动作及推荐 **L3 最小护栏配方**：

| 目标类型 | 典型用户动作与最小输入 | 怎么观测结果（证据） | 推荐 L3 最小护栏配方 |
| --- | --- | --- | --- |
| `lib` | 在隔离安装环境中导入公开 API，用小 fixture 执行核心变换或计算。 | 返回值、异常类型与包内资源加载均符合预期，保留回归结果。 | 禁止 `src/` 反向导入 `examples/`/`scripts/`；隔离安装烟雾测试。 |
| `app` | 从真实入口（CLI、Web 路由、插件或无硬件 ROS `launch`）处理一条代表性样本（如标注→修改→撤销，或回放已知消息）。 | 重开后状态、话题、坐标系或输出与预期一致；产物仅落入忽略目录。 | 层/进程越界导入检查；敏感/标定文件入库拦截；入口回放测试。 |
| `assets` | 用目标加载器打开一个带相对网格与贴图引用的代表性模型。 | 网格完整解析、单位与关节方向正确，记录加载器版本。 | 相对路径可解析检查；逐项 `LICENSE` 与元数据存在性检查。 |
| `dataset` | 按发布清单读取一个样本及对应划分，校验字段与摘要。 | 哈希与 Schema 匹配，训练与留出集标识无交集。 | Manifest 校验和检查；Schema 单一权威校验；Split 泄漏断言。 |
| `content` | 从首页打开一篇代表性正文并跟随链接直达目标资料；必要时执行本地构建。 | 导航可达、图片加载正常、构建或导出零报错。 | 全仓本地链接与媒体文件存在性扫描；构建产物烟雾检查。 |
| `research` | 按主报告记录的配置、数据版本与固定小样本重算一个关键指标。 | 重算结果落在报告声明的容差与聚合口径内，记录运行 ID。 | 报告元数据完整性检查（`code_rev`/`config`/`dataset_ver`/`run_id`）。 |
| `workspace` | 从干净检出按组件清单核对两个成员仓并执行一次跨组件握手。 | 各成员仓提交与清单一致，跨组件样本或接口传递成功。 | 组件提交锁定检查；禁止根层硬编码本机路径；无硬件握手脚本。 |

### 实例：灵巧手数据与 tracker 的 L2 + L3 组合

为防止坐标系或尺度错误一路渗透到训练端，把约定落到接口与回归样本而非口头说明：
- **L2 接口护栏**：采集端写出坐标系与长度单位，标注端沿用同一会话定义，训练数据读取入口强制校验这两项字段，缺失时立刻报错并指明缺失字段名。
- **L3 回归样本**：保留两条极小样本——一条合法轨迹验证关节方向与尺度，一条故意缺单位的负样本验证读入阶段准确拦截。
- **算法表现证据**：锁定配置与权重后，在同一版数据和留出集复核跟踪指标，报告同时保留最差动作与对应回放。目录完整、程序跑通与追踪质量各自留证，互不替代。

## 4. 本仓自身的 L3 护栏范例（Dogfooding）

本仓用单文件、零外部依赖的 [scripts/check_release.py](../scripts/check_release.py) 约束自身契约（仅需 Python 3.8+）：

```bash
python3 scripts/check_release.py --tag v2.0.0
```

该脚本离线校验：版本号跨文件同步、6 类核心原型与 `workspace` 拓扑定义完整性、每个类型卡片是否写齐四段边界与不变量契约、验收表全覆盖、技能参数对齐以及全仓站内相对链接零断裂；任一项失败均输出带文件路径与修复动作的提示。

业务仓的实测验证命令见[工作流程实例](research-development-workflow.md)。
