# 仓库类型与目录模板

> 已确认采用软件型、ROS 系统型、资产型、数据发布型四类标准仓库。下列目录细节为可修订的设计，不是已经生成并验证的代码模板。目录中的 `<name>` 等是说明占位符；所有可选项只在确有内容时创建。模板类型不决定 Git 仓库数量。

依据见[学习与仿真](research-learning-simulation.md)、[遥操作与资产](research-teleop-assets.md)、[系统与数据发布](research-systems-data.md)研究记录。下列目录树是综合后的建议，不是任何一个上游仓库的原样复制。

## 1. 如何选择

先问仓库主要交付什么，再看构建工具，不先问项目叫 RL 还是 teleop。

| 类型 | 主要交付物 | 适用方向 | 不适用情况 |
| --- | --- | --- | --- |
| A 软件型 | 可安装的库、命令或应用 | RL、VLA、仿真任务、感知、离线处理、非 ROS 遥操采集 | 纯资源或纯数据发布不需要完整软件骨架 |
| B ROS 系统型 | ROS 包、消息、驱动和启动配置 | 在线控制、导航、规划、ROS 遥操采集、系统集成 | 只用 Python 调用 SDK 不必选 B |
| C 资产型 | 可被多项目消费的模型与场景资源 | 机器人、物体、环境、共享场景 | 大量采集轨迹和训练权重不属于物理资产 |
| D 数据发布型 | 版本化数据集说明、清单、分割和格式定义 | 采集数据发布、训练数据集、评估集 | 数据处理程序本身通常选 A |

A/B 的主要区别是构建和发布组织，不是“研究／生产”二分。一个 ROS 驱动库也可能只有一个包；一个 Python 项目也可以长期用于生产。

有多个方向时先组合本仓内部模块，只有独立版本、使用者、许可、存储或运行环境确实需要时才拆仓。不为“以后可能复用”立即建立公共仓库。

## 2. A：软件型

### 默认 Python 布局

```text
<project>/
├── src/<package>/          # 正式实现；内部按功能组织
├── configs/                # 用户选择的运行配置，可选
├── assets/                 # 少量项目专属资源／获取清单，可选
├── scripts/                # 安装、下载等辅助入口，可选
├── examples/               # 面向使用者的可运行示例，可选
├── tests/                  # 关键行为、小型 fixture
├── docs/
├── outputs/                # 本地运行生成，忽略提交
├── pyproject.toml
├── <环境清单与锁文件>       # 按生态选定，不创建这个字面文件
├── .gitignore
└── README.md
```

`examples/` 展示如何使用已有实现，不复制实现。笔记本确有探索和分析用途时可加 `notebooks/`，正式功能移入源码包；不要求每个实验都变成框架模块。

纯 Python 且适合当前依赖时可优先 Pixi；上游明确使用 uv、Conda、容器或模拟器运行环境时，保留验证过的方案。环境选择与目录标准分离。发布包元数据和运行环境锁文件职责不同，但同一依赖约束不要在多个文件里手工维护冲突副本。

### 同一骨架的业务变体

下表是候选模块名，不是每个项目都必须包含的目录。小项目可先用同名 `.py` 文件。

| 方向 | `src/<package>/` 可按这些职责组织 | `configs/` 可按需分类 | 大文件／输出 |
| --- | --- | --- | --- |
| RL／模仿学习／VLA | `policies/`、`training/`、`evaluation/`、`datasets/` | `experiments/`、`policies/`、`datasets/` | 权重与数据外置，训练结果按 run 保存 |
| 仿真／任务基准 | `envs/`、`tasks/`、`sensors/`、`rendering/` | `tasks/`、`scenes/`、`robots/` | 共享资源按版本获取；轨迹、视频是产物 |
| 遥操作／在线采集 | `inputs/`、`robots/`、`recording/`、`runtime/` | `robots/`、`cameras/`、`sessions/` | 实际标定外置，episode 进入数据存储 |
| 离线数据处理 | `reading/`、`transforms/`、`rendering/`、`exporting/` | `pipelines/`、`cameras/` | 源数据只读引用，导出到独立目标 |
| 感知／重建 | `perception/`、`tracking/`、`reconstruction/` | `models/`、`sensors/` | 预训练权重外置，重建资产显式发布 |
| 运动学／规划／控制算法 | `kinematics/`、`planning/`、`control/` | 仅实际可配置部分 | 基准输入可用小 fixture，结果不进源码 |

`datasets/` 在源码包里表示数据读取／变换代码，不表示数据实体。`models/` 若用于神经网络结构，应在文档说清楚；实体权重用 `checkpoints` 或明确的外部 URI，机器人模型归资产。

### Python 配置与文件配置

- 用户常改的现场值和运行选择适合 `configs/` 中的 YAML/JSON/TOML。
- 依赖类、函数、类型检查的任务定义或配置类可与实现在源码包内相邻；不要强制改写成 YAML。
- 同一参数只有一个权威定义。根目录配置可以引用代码默认值，不再复制完整的第二份默认表。
- 需要随包安装的默认资源放包内，并通过包资源机制加载；根目录示例不应成为安装后偷偷依赖的文件。

### 多包／框架扩展变体

当训练服务端与轻量控制客户端需要不同依赖，或仿真框架要求扩展包时，A 可以多包，不必另造一种按业务命名的模板。依据是 openpi 的独立客户端包与 Isaac Lab 的多扩展结构，见[研究记录](research-learning-simulation.md)。

新自有多包项目可采用：

```text
<project>/
├── packages/
│   ├── <main_package>/
│   │   ├── src/<main_package>/
│   │   ├── tests/
│   │   └── pyproject.toml
│   └── <client_package>/
│       ├── src/<client_package>/
│       ├── tests/
│       └── pyproject.toml
├── configs/                # 跨包运行组合，按需
├── docs/
└── README.md
```

这不是要求把所有业务模块都包装成可发布包。扩展 Isaac Lab 等既有框架时，保留它要求的 `source/`、扩展元数据和注册位置，而不是机械改名成 `packages/`。多包也不意味着共享一个不兼容的 Python／CUDA／SDK 环境。

### 原生库变体

当主要交付物是 C++ 库，或混合语言构建需要时，A 使用以下变体，而不是硬套 Python 路径：

```text
<project>/
├── include/<project>/      # 对外头文件
├── src/                    # C++／CUDA 实现
├── bindings/               # Python 等语言绑定，按需
├── cmake/                  # 构建辅助，按需
├── examples/
├── tests/
├── benchmarks/             # 性能基准程序，按需
├── docs/
├── CMakeLists.txt
└── README.md
```

小型 Python 扩展可以保持 A 默认布局，由构建后端明确扩展源码位置；不要因此新建第二个业务实现仓库。纯 Python 项目无需上述 C++ 目录。基准结果进入输出目录，不和基准程序混放。

## 3. B：ROS 系统型

下面是源码仓库，不是整个本地工作区：

```text
<robot_system>/
├── <name>_interfaces/      # 只有自定义消息确实需要独立包才创建
│   ├── msg/               # srv/、action/ 按需
│   ├── CMakeLists.txt
│   └── package.xml
├── <name>_driver/
│   ├── include/<name>_driver/
│   ├── src/
│   ├── test/
│   ├── CMakeLists.txt
│   └── package.xml
├── <name>_bringup/
│   ├── launch/
│   ├── config/            # 保留 ROS 常见包级命名
│   ├── CMakeLists.txt
│   └── package.xml
├── docs/
├── dependencies.repos     # 需要源码依赖组合时才有，固定版本
└── README.md
```

- 单包项目可把该包内容直接作为仓库根目录；不强制创建三包。
- Python ROS 包保留 ament Python 所需的包目录、资源标记与构建文件，不要求再次嵌入普通 Python `src` 布局。
- `launch/` 是正式启动描述，不归入临时辅助脚本。
- bringup 可按需有 `maps/`、`rviz/` 等包级资源；不要在根目录再复制另一份。
- 共享机器人描述可独立发布为 description 包，也可由 C 型资产仓库提供；不要求复制资源。
- 包级测试就近维护；跨包场景确有需要时增加系统验证包或明确的根级验证目录，不机械复制每层测试。

典型本地工作区另有 `src/<robot_system>/`，其 `build/`、`install/`、`log/` 是构建产物，不提交进源码仓库。不将“仓库移动进 workspace/src”理解为重构所有包内部目录。

## 4. C：资产型

资产是主交付物，因此分类可直接放根目录，不再套 `assets/assets` 或空源码包：

```text
<asset_library>/
├── robots/<asset_id>/
├── objects/<asset_id>/
├── environments/<asset_id>/
├── scenes/<scene_id>/      # 仅确实发布组合场景时创建
├── manifests/             # 外部资源版本、获取位置及校验信息，按需
├── tools/                 # 导入、转换、检查工具，按需
├── docs/
└── README.md
```

不是每个资产仓都需要三类资源。只保存机器人的项目可仅有 `robots/`；引擎或发行包要求扁平路径时保留其约定并提供索引，不为了目录美观破坏引用。

### 单项资产

以下是自有资产建议布局，不是要重排所有厂商原包：

```text
<asset_id>/
├── README.md              # 来源、单位、坐标、版本、格式与适用范围
├── LICENSE                # 或准确的逐项许可说明／引用
├── model.urdf             # MJCF/USD/glTF 等按真实格式保留
├── meshes/                # 可进一步区分 visual/collision
└── textures/              # 按需
```

- 稳定资产 ID 与可变显示名称分开考虑；不能仅以本地绝对路径识别资产。
- 原始 CAD／扫描如需保存，标清它是权威来源；转换输出记录源版本及转换方式。
- 不强制所有资产都转成同一格式，也不假设存在视觉网格就存在物理碰撞、惯性或接触参数。
- 多种表示可以同时是正式发布产物，不能一概当缓存删除；仅可重建的临时转换结果才放忽略目录。
- 许可按资产核查；代码仓库的许可证不能自动覆盖外部模型、纹理和扫描。
- 规模大或受许可约束的资源通过清单下载到外部缓存，仓库保存可获取的版本引用与校验信息。

### 场景到底放哪里

| 文件是什么 | 归属 |
| --- | --- |
| 桌子／房间等可复用静态模型 | `environments/<id>/`，软件仓内则为 `assets/environments/` |
| 多个资产实例及摆放关系组成的可复用 USD/MJCF 场景 | C 型 `scenes/<id>/`；小型软件仓可为 `assets/scenes/` |
| 某次任务的数量、摆放范围、相机选择 | 软件仓 `configs/scenes/` |
| reset、随机化、奖励、终止和成功判定代码 | 软件源码中的任务模块 |
| 一次运行实际采样出来的摆放和物理参数 | 运行记录或 episode 元数据 |
| 导航地图／路线图 | 所属导航配置包，或作为版本化环境资源发布 |

这些是不同文件，不应为“统一场景目录”强行合并。

## 5. D：数据发布型

数据集是主交付物时使用。下面是我们建议的目录，不宣称任何上游项目采用了完全相同的布局：

```text
<dataset_release>/
├── README.md              # 数据说明、来源、许可、用途与限制
├── schemas/               # 可执行格式定义；纯说明也可仅放 docs
├── manifests/             # 版本、文件索引、存储 URI、校验信息
├── splits/                # 明确版本的训练／验证／测试划分，按需
├── samples/               # 可合法发布的小样本，按需
├── tools/                 # 薄下载／检查入口，按需
└── docs/
```

- TB 级视频、HDF5、Parquet、bag 等数据实体通常位于对象存储或数据发布平台，不装进普通 Git。
- 发布平台自带的数据布局和元数据优先，不强制把平台字段复制成另一份清单。
- 原始／处理后数据与发布版本应可区分；不可只靠 `final`、日期或手工重命名代表版本。
- 格式版本与数据版本不同，清单说明使用哪个格式；别把某个当前 schema 数字写成永久目录标准。
- 格式定义只有一个权威位置。消费者引用版本化定义，不在每个训练仓重复维护。
- 完整清洗、渲染、导出算法归 A 型软件；如果数据仓自己的工具已经形成软件包，也可以在同仓增加 A 的源码布局，不要求拆 Git 仓库。
- 外部数据路径、字段和许可需要可验证；示例路径不意味着资源已经存在。

## 6. 可组合，但不默认创建的扩展

| 扩展 | 何时创建 | 不应变成 |
| --- | --- | --- |
| `deploy/` | 有实际容器、服务或设备部署描述 | 另一套业务实现、密钥仓库 |
| `environments/` | 一仓确需多个不兼容环境定义 | 所有小项目的强制层级；与资产环境模型混淆 |
| `benchmarks/` | 需要独立性能或任务评估程序 | 测试输出大文件堆 |
| `schemas/` | 确有机器可读外部格式契约 | 自动生成绑定的另一份手工源码 |
| `third_party/` | 必须随仓维护的第三方源码 | 随意复制全部依赖 |
| `packages/` | 确有多个独立安装／发布的软件包 | 为每个 Python 子模块增加一个包 |
| `notebooks/` | 探索、解释和分析确实需要 | 生产流水线的唯一实现 |

同一仓不要同时用 `docker/` 与 `deploy/docker/` 存两套同用途配置。既有生态约定优先；上表是新自有项目默认建议，不是重命名第三方项目的指令。

## 7. 不推荐的收敛方式

1. 按 RL、VLA、Sim、teleop 分别复制几乎一样的模板，导致规范漂移。
2. 把所有方向都塞进一个必选目录树，产生大量空层。
3. 强制资产仓、ROS 包、C++ 库采用 `src/<python_package>/`。
4. 把源代码仓库、运行工作区、数据发布目录视为同一件事。
5. 只整理目录，不说明其中是代码、资源、参数还是运行生成物。

四类模板已确认为本规范的组织方式。后续先在所属类型内细化目录，不因增加一个业务方向就新增模板；若遇到现有类型无法自然表达的构建或交付差异，再讨论是否调整分类。
