# standard-repo · 项目仓库设计规范

**v1.0.0** 面向同时维护多个软件、机器人、数据和研究项目的人。按主要交付物选仓库布局，按研究方向建立项目索引。两者通过主仓链接关联。[版本说明](CHANGELOG.md)

## 从手上的任务开始

| 现在要做什么 | 在哪里做 | 完成的标志 |
| --- | --- | --- |
| 开发功能 | 进入实际 Git 工作副本，按 README 和依赖清单启动已有入口。 | 使用者能在 CLI、页面或设备接口上用到这项改动。 |
| 测试或复核 | 在该仓运行受影响的快测或短回放。研究项目同时记录数据版本、配置、权重和指标。 | 别人能找到验证命令、输入和结果，知道哪些行为已经验收。 |
| 整理多个项目 | 在方向索引登记主要交付物、主仓、运行位置和最近验证。同一项目在多台机器有副本时，共用一条记录。 | 从索引可以找到要改的仓、要用的环境和最近一次可复核的产出。 |

[开发与测试实例、跨主机索引示例](docs/research-development-workflow.md) · [七类仓库的目录设计](docs/repository-types.md) · [基于 Lauren Tan 演讲的验证设计](docs/verification.md)

## 按主要交付物选型

| 类型 | 主要交付物 | 项目中的例子 |
| --- | --- | --- |
| A 软件 `software` | 可运行的工具、应用、库、服务或插件 | Data Viewer、Macaron 插件与 WebUI、RSI Lab 自动化框架 |
| B ROS 系统 `ros` | 按 ROS 包构建、启动的系统 | Tianji 遥操作、ROS 设备驱动 |
| C 资产 `assets` | 可独立复用的物理模型、设计资源或场景 | Wuji 描述、CAD、URDF |
| D 数据发布 `dataset` | 有版本的数据集、清单与格式 | 灵巧手数据金字塔的一版数据 |
| E 知识与出版 `content` | 供人阅读的知识、规范、论文或站点内容 | 研发知识库、个人学术主页、本规范 |
| F 实验研究 `research` | 能追溯到协议、输入和证据的研究结论 | SPD 闭环评估报告、冻结数据上的方法对比 |
| G 集成工作区 `workspace` | 独立组件的版本组合、接口与联调入口 | 遥操作多仓工作区及其子模块清单 |

一个方向可以包含多类仓库。比如动捕采集和动作标注可以在一个软件仓中共享会话标识、时间戳和坐标系，各自提供入口。数据开始独立发布时，用 D 记录版本和划分。围绕固定数据交付对照实验时，用 F 组织报告。普通项目目录只需索引；需要交付一组能联调的组件时再选 G。

## 用 OMP 试做一次整理

只阅读规范可直接打开上面的文档。要让 OMP 对现有仓库出方案，在 Linux 上用 Git 克隆整个固定版本，再注册技能。以下命令适用于首次安装，已有安装可用最后一行检查指向。

```bash
git clone --branch v1.0.0 --depth 1 https://github.com/suzhelearning/standard-repo.git standard-repo-v1
mkdir -p ~/.omp/agent/skills
ln -sT "$(realpath standard-repo-v1/skills/standardize-repo)" ~/.omp/agent/skills/standardize-repo
readlink -e ~/.omp/agent/skills/standardize-repo/SKILL.md
```

保留克隆目录，技能会从真实路径读取同一版本的规范。在新的 OMP 会话中，把路径替换成实际代码仓库，先查看只读方案：

```text
/skill:standardize-repo /path/to/project --plan
```

方案会列出主类型、判定依据、路径映射和验证方法。需要实施时可去掉 `--plan`。省略路径会使用当前工作目录。支持 `--type auto|software|ros|assets|dataset|content|research|workspace`，默认自动识别。大数据、权重、设备操作、跨仓变更和覆盖冲突按技能中的授权范围处理。[迁移技能及验收规则](skills/standardize-repo/SKILL.md)

## 仓库内的共同规则

### 按内容归属，不按文件后缀归属

- 正式实现放源码包或构建系统规定的位置。
- 用户选择的运行参数放配置位置；有逻辑的配置类可与源码相邻。
- 模型与网格是资产；由模型生成的 episode 是数据，不能混为一类。
- 薄辅助入口放 `scripts/` 或纯资源仓的 `tools/`，不复制第二套业务实现。
- 文档展示图片默认放 `docs/media/`，不与物理资产混放。
- 日志、视频、报告和 checkpoint 等运行生成物不进入正式源码目录。

### 不创建空架构

目录按需要出现，不把模板树全部实例化。一项功能先用一个文件，复杂到需要拆分再变成目录。

不默认引入 `core/`、`common/`、`managers/` 等难以判断归属的层。工具按用途命名，例如 `transforms.py`、`timestamps.py`，不建无限扩张的 `utils.py`。

### 安装和路径不依赖开发机偶然状态

- Python 包使用项目专属名称，不跨仓堆叠同名顶层包。
- 不靠修改 `sys.path` 或相邻仓库源码目录完成正常使用。
- 随安装包分发的默认配置和小资源通过包资源机制定位。
- 新自有文件配置中的相对文件路径默认相对于声明它的配置文件；ROS 资源 URI、引擎引用和现有配置框架保留原有明确语义，不强行改写。
- 依赖清单、锁文件和版本化资源引用应能说明环境来源。Pixi 是可选默认工具，不是所有项目的强制规范。

### 源码、资产、数据和产物有不同生命周期

- Git 管源码、配置、文档及适量小资源；大资源可通过 LFS 或外部存储交付，具体按许可与使用方式决定。
- 大型数据集和预训练权重默认外置，版本与获取方式需要可追溯。
- 共享资产只有一个权威来源；本地缓存不变成另一份随意修改的源模型。
- 正式发布的转换模型不一定是可删除缓存；必须区分源文件、发布表示和临时产物。
- 数据格式版本、数据集版本、代码版本分别记录，不强制永远同步编号。

### 现场信息与公共默认值分开

配置示例可以提交，实际设备连接信息按敏感性管理，密钥与个人标定默认外置。无需把普通非敏感机器人几何参数也当成秘密。

本地覆盖配置由 Git 忽略；运行有效配置可随结果保存，但先移除密钥等敏感值。不反写默认配置。

### 运行结果默认集中，尊重工具约定

新自有应用建议使用 `outputs/<run_id>/` 存本次配置快照、日志、报告和视频；长期采集数据另有明确存储位置。

ROS 的 `build/`、`install/`、`log/`，以及构建工具自己的缓存保留原约定并忽略提交，不为了“所有输出一致”重写工具行为。

### 入口与说明保持唯一

README 说明职责及使用入口。软件说明安装与运行，内容项目给出阅读与出版入口，实验说明复核方法，集成工作区说明组件组合；长说明放 `docs/`。同一主题只有一处权威说明，其他位置链接过去。

正式命令由所属工具链声明，调用已有实现。部署、示例、笔记本不能各维护一套算法。

不以 `old/`、`new/`、`backup/` 保留并行实现；历史由 Git 管理。真实需要支持的格式版本必须有明确用途，不等同于备份目录。
